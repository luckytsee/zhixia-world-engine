# 06 记忆系统设计

> **第一阶段的真正难点不是接 API，是"记什么"。**
> 这一份文档是整个项目里最需要反复迭代的部分。

---

## 1. 为什么记忆比 LLM 难

接 DeepSeek API 是一下午的事。难的是：

- 昨天作者说他朋友叫小明，今天能不能想起来？
- 三周前作者说过"我讨厌周一开例会"，今天周一，该不该提？
- 作者昨天纠正过"别叫我某个称呼"，今天还会不会犯？
- 三个月前的一次闲聊，还该不该在 prompt 里占位置？

**这些问题没有"接个库"的答案。** 这是一个设计问题，需要真实使用数据来调。

---

## 2. 记忆分层

不要用一个"长期记忆库"解决所有问题。分三层，各自的存储、检索、生命周期完全不同。

```
┌─────────────────────────────────────────────────┐
│ ① 工作记忆 Working Memory                        │
│    当前对话最近 N 轮                              │
│    存储：内存 / 环形缓冲                          │
│    生命周期：会话结束即丢                          │
│    容量：20 轮（可配）                            │
├─────────────────────────────────────────────────┤
│ ② 情景记忆 Episodic Memory                       │
│    "什么时候发生过什么"                            │
│    存储：SQLite + 向量索引                        │
│    生命周期：衰减，半年以上自动归档                 │
│    容量：无硬上限，但有衰减权重                     │
├─────────────────────────────────────────────────┤
│ ③ 语义记忆 Semantic Memory                       │
│    "关于作者我知道什么"（抽象后的事实）              │
│    存储：结构化表（key-value / 图）                │
│    生命周期：**长期，但可被推翻**                   │
│    容量：几十到几百条，必须精简                     │
└─────────────────────────────────────────────────┘
```

### 2.1 工作记忆

就是对话历史，但有两个要点：

- **不能无限增长。** 20 轮之后要用摘要压缩，摘要本身也是一种记忆。
- **摘要要保留"未完成的事"**，比如"作者说要发我一份文档但还没发"。这类信息丢了会显得非常失忆。

### 2.2 情景记忆

**存的是"事件"，不是"对话原文"。**

```python
@dataclass
class Episode:
    id: str
    timestamp: float
    summary: str           # 一句话摘要，不是原文
    participants: list[str]
    emotion: str | None    # 当时的情绪基调
    topics: list[str]      # 标签，用于检索
    importance: float      # 0-1，影响衰减速度
    source_turns: list[str]  # 原始对话的引用（可选，用于追溯）
```

**关键设计：存摘要而不是原文。**

理由：原文检索出来的东西是噪声（"哈哈是啊"也存进去了），摘要才能作为记忆用。**摘要在对话结束时由 LLM 生成，这是值得花的钱。**

#### 重要性评分

`importance` 决定了这条记忆衰减多快。建议由 LLM 在生成摘要时同时输出，评分标准：

| 分值 | 类型 | 例子 |
|---|---|---|
| 0.9-1.0 | 身份/关系/重大偏好 | "他朋友叫小明"、"他讨厌被叫某个称呼" |
| 0.6-0.8 | 持续性的项目/计划 | "他在做一个桌面 AI 项目" |
| 0.3-0.5 | 一般事件 | "今天调试了一下午 bug" |
| 0.0-0.2 | 闲聊 | "聊了会儿天气" |

**低分记忆不是立刻删除，而是检索权重低 + 衰减快。** 这样既不占 prompt，又不会真的丢失。

### 2.3 语义记忆

**这是最容易被做烂的一层。** 它是从情景记忆里**抽象**出来的稳定事实。

```python
@dataclass
class Fact:
    key: str              # "user.friend_name"
    value: str            # "小明"
    confidence: float     # 0-1
    first_learned: float
    last_confirmed: float
    evidence: list[str]   # 支持这条事实的 episode ids
```

**为什么必须有 `confidence` 和 `evidence`**：LLM 会理解错。作者说"我朋友小明"，如果被抽成 `user.friend_name = 小明`，就是错的。**有 evidence 才能追溯，有 confidence 才能在被推翻时不纠结。**

#### 事实的三种状态

| 状态 | 含义 | 处理 |
|---|---|---|
| 已确认 | 作者明确说过，或多条证据支持 | 注入 prompt |
| 待验证 | 单条低置信证据 | **不注入**，但保留 |
| 已推翻 | 作者明确否认，或长期无证据 | 标记删除，不再注入 |

**"待验证的事实不要注入 prompt"是个重要纪律。** 把不确定的东西说出口，比失忆更糟——失忆只是没记住，说错是"他根本不了解我"。

## 3. 检索

### 3.1 检索什么、什么时候检索

| 时机 | 检索什么 |
|---|---|
| 作者发言后 | 相关情景记忆（向量检索）+ 相关事实（key 匹配） |
| 主动发言前 | **当前情境相关**的情景记忆（不是作者刚说的话） |
| 对话结束时 | 不检索，只写入 |

**注意主动发言的检索路径不同**：没有"作者刚说的话"可以拿去查向量库，只能拿当前情境（前台进程、时间段、最近活动）去查。这意味着**情景记忆的 `topics` 标签必须包含"情境"信息**，否则主动发言时检索不到东西。

### 3.2 混合检索

单靠向量检索不够。建议：

```
最终得分 = w1 × 向量相似度
         + w2 × 时间新近度（指数衰减）
         + w3 × importance
         + w4 × 关键词命中（实体名精确匹配）
```

**`w4` 关键词命中不能省。** 向量检索对"小明"这种人名很不可靠——它可能召回一堆"聊天"类记忆。**实体精确匹配是刚需。**

### 3.3 注入格式

记忆进 prompt 时必须**带时间**，否则 LLM 会说出"你昨天说的"（其实是三个月前）。

```
【关于作者】
- 朋友叫小明（2026-03 确认）
- 讨厌周一开会（2026-09 提到过两次）
- 正在做桌面 AI 项目（2026-09-22，进行中）

【相关回忆】
- 2026-09-20：他调试 Live2D 透明窗口折腾了一晚上
- 2026-09-15：他说过想给这个 AI 加主动行为
```

**格式要点**：
- **分两块**：稳定事实 vs 相关回忆。前者给"你是谁"，后者给"最近怎么了"。
- **每条带日期。**
- **条数硬限制**（事实 ≤ 10 条，回忆 ≤ 5 条）。宁可少，不要多——prompt 里的噪声会直接变成胡话。

## 4. 遗忘

**不遗忘的记忆系统 = 没有记忆系统。**

### 4.1 三层遗忘机制

| 机制 | 对象 | 规则 |
|---|---|---|
| 时间衰减 | 情景记忆 | 检索得分按 `exp(-Δt / half_life)` 衰减，半衰期默认 30 天，**按 importance 缩放** |
| 容量淘汰 | 情景记忆 | 超过 N 条时，淘汰"低 importance + 久未命中"的 |
| 事实过期 | 语义记忆 | `confidence` 随时间下降；被推翻的直接删除 |

**importance 缩放半衰期**（重要的事忘得慢）：

```
effective_half_life = half_life_days * (1 + importance * 3)
```

importance=1.0 的记忆半衰期是 120 天，importance=0.1 的只有 39 天。

### 4.2 不能忘的东西

**有些记忆永远不衰减**：

- 作者明确说"记住这个"的内容
- 被作者纠正过的偏好（"别叫我某个称呼"）
- 身份类事实（名字、称呼）

**给这些加一个 `pinned` 标志。** 作者的纠正特别重要——**同样的错误犯两次，信任就没了。**

### 4.3 遗忘的可见性

建议做一个命令让作者能看和删记忆：

```
/memory list          # 列出所有语义记忆
/memory forget <key>  # 删除某条
/memory why <key>     # 显示这条记忆的来源
```

**`/memory why` 特别重要**——它让作者知道"它为什么知道这个"。没有这个，作者会不安（"它怎么知道我住哪"）。

## 5. 写入时机

| 时机 | 写什么 |
|---|---|
| 每轮对话后 | 更新工作记忆 |
| 会话结束 / 空闲 5 分钟 | 生成情景摘要 + 抽取事实（**一次 LLM 调用做完两件事**） |
| 作者明确说"记住" | 立即写入，`pinned=True`, `importance=1.0` |
| 作者纠正 | 立即覆盖旧事实，旧事实标记"已推翻" |

**"空闲 5 分钟"这个触发点值得注意**：会话结束很难定义（作者可能只是走开），但连续 5 分钟没输入基本可以确认这一轮聊完了。**这是个便宜的启发式。**

## 6. 存储选型

| 层 | 选型 | 理由 |
|---|---|---|
| 工作记忆 | 内存 deque | 不需要持久化 |
| 情景记忆 | **SQLite + sqlite-vec**（或 chromadb） | 单文件、无需服务、Windows 友好 |
| 语义记忆 | SQLite 普通表 | 结构化，几十到几百条，不需要向量 |

**不推荐一开始就上数据库服务**（Postgres / Redis）。桌面宠物是单作者单进程，SQLite 完全够，而且**没有运维负担**。

### 6.1 ⭐ Embedding 用本地，零成本

**本机已装 `sentence-transformers 5.5.1`**（2026-09-22 实测）。

**含义：语义检索的向量化可以完全本地跑，不产生任何 API 费用。**

| 模型 | 大小 | 建议 |
|---|---|---|
| **`paraphrase-multilingual-MiniLM-L12-v2`** | ~120MB | ⭐ **推荐**（多语言，中文可用） |
| `BAAI/bge-small-zh-v1.5` | ~100MB | 中文效果更好 |

**⚠️ 模型还没下载**（缓存目录是空的），第一次用需要下载。建议把缓存指向 D 盘：

```
HUGGINGFACE_HUB_CACHE = D:\models\hf
```

**⚠️ 注意**：embedding 模型很小（100MB 级），**CPU 推理完全够用**（一篇文本几毫秒），不需要 GPU。**不要为它折腾 AMD 显卡加速。**

### 6.2 ⚠️ 不要用云端 embedding API

理由不只是省钱（虽然确实省钱）：

| 云端 embedding | 本地 embedding |
|---|---|
| 每次检索都要联网 | 离线可用 |
| 按量计费 | 免费 |
| **记忆内容要发给第三方** | **数据不出本机** |

**最后一条最重要**：记忆里包含大量私人信息（人名、偏好、生活细节）。**这部分数据不应该发给任何第三方。**

⚠️ **注意**：**LLM 调用本身无法避免要发出去**（这是 DeepSeek API 的性质），但**上下文里应该只放检索后的少量相关记忆**，而不是全部记忆。这是 [02_阶段一](02_阶段一_会聊天.md) 限制"事实 ≤10 条、回忆 ≤5 条"的另一个理由。

⚠️ **注意**：不要在 Windows 上用需要编译的向量库（如某些 faiss 版本），会卡在构建工具链上。优先选纯 Python 或预编译 wheel 的方案。

## 7. 这一层的验收标准

- [ ] 能记住作者的名字、称呼偏好，并在 100 轮后依然正确
- [ ] 作者纠正过的内容不会重复犯错
- [ ] 三周前的闲聊**不会**出现在 prompt 里（衰减生效）
- [ ] 三周前的重要事实**会**出现在 prompt 里（importance 生效）
- [ ] `/memory why <key>` 能追溯每条记忆的来源
- [ ] 情景摘要的生成不阻塞对话（异步）
- [ ] 全部记忆可以用一个命令导出成可读文本（用于人工检查）

**最后一条是调试手段**：隔一周把记忆导出来看一遍，你会立刻发现"它记住了很多垃圾"或者"它忘了最该记的"。**这个人工检查环节在早期比任何自动化指标都有用。**
