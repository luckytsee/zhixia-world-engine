# 04 · 扩展方向：接进一个真实聊天软件（思路）

> 讲**机制和坑**，不给可直接运行的代码。仓库主体不含 IM 实现——它天然携带真实社交关系。
> 这一篇的价值是：把"接到真实 IM 上"会撞到的几件具体事讲清楚，
> 包括那些只有真跑过才知道的地方。

---

## 一、人类发消息的方式，和聊天机器人完全不一样

这是接 IM 最先撞上的事，也是最值得单独讲的一条。

### 1.1 对方会连着发好几条

真人聊天不是一问一答：**"在吗" / "问你个事" / "那个东西弄好了吗" / [表情] / "咋不理我了"**
——五条消息其实是一句话。

两种处理方式，各有代价：

| 做法 | 好处 | 代价 |
|---|---|---|
| **攒批**：等一小段时间，把连发的几条合并成一条喂给她 | 上下文完整、省调用 | ⚠️ **她会只回最后一条**——前面问的事一个字没答 |
| **逐条**：来一条处理一条 | 每条都被照顾到 | 回得很碎，节奏像机器人 |

**实测结论**：攒批更自然，但**必须显式要求她"每一条都要照顾到，不要只回应最后一条"**，
否则用户会得到"最早的问题被跳过、只好再问一遍"的体验。

⚠️ 合批时**用换行把几条分开**（而不是拼成一段），并明确告诉她"对方连着发了几条"。
这是给模型的信号，不是给人看的。

### 1.2 有些消息你根本收不到内容

**微信的语音消息是 SILK 格式、不是文件**，很多方案拿不到内容。**图片**也类似。

⚠️ 这里最容易犯的错是**装作听懂了**。必须明确要求她**如实说"语音我这儿听不了，你打字呗"**，
并且**绝对不许猜内容**——猜错比说不懂糟得多（对方会以为你听到了却答非所问）。

### 1.3 回复的条数要克制

**默认 1–3 句**，只在对方明确要求详细说时才放开。理由：

- IM 里长段落很突兀（微信里没人这么说话）；
- 一次回一大段，会显得"她憋了半天"；
- **连续刷屏是模型不守规矩时最常见的表现**——条数上限同时也是安全阀。

## 二、记忆隔离：谁都不能知道别人存在

**这是整个 IM 接入里设计得最重的一块**，也最容易做错。

### 2.1 隔离规则：星形，不是网状

```
        你（本人：能看全部）
        /   |   \
       甲    乙    丙      ← 每个人只能看「你 + 自己」
                            甲乙之间互相看不见，甚至不知道对方存在
```

- **每个人**看到的：关于你的事实 + 关于他自己的事实；
- **默认**：甲的档案、甲说过的话、甲和你的关系——**乙一条都看不到**；
- **你**（本机，或在 IM 里以"本人"身份出现）：能看全部。

### 2.2 为什么必须这么设计

1. **串味会让角色崩坏**——如果甲的偏好混进乙的对话，她会对乙说出甲的事，
   对方立刻会意识到"她跟别人也这么聊"；
2. **隐私是别人的**——朋友告诉她的私事属于那个朋友，不该变成你随口能问出来的东西；
3. **一旦泄露不可撤回**——发出去的消息就是发出去了。

### 2.3 怎么实现隔离

核心是**给每条记忆打上"属于谁"的标记**，然后**在检索之后、注入之前**按标记过滤。

| 方式 | 做法 | 注意 |
|---|---|---|
| **键名前缀**（推荐） | 事实的 key 带归属，如 `甲.作息` | 判归属不用猜，看前缀即可；代价是键名变长 |
| **独立分区** | 每个联系人一张表/一个库 | 隔离最硬；跨联系人查询会变麻烦 |
| **字段标记** | 加一列 `subject` | 灵活；**必须保证每条写入都带上**，漏一条就是漏洞 |

⚠️ **三条实操教训**：

1. **过滤要在"检索之后、注入之前"**——先按相关性多取（比如 200 条），**再**按归属分组，
   否则还没分组就被 top-k 截断了，某个人的事可能被挤没；
2. **按组给配额**，别让大家抢同一批位置。否则会出现"关于你的 5 条 + 甲的 5 条"占满名额，
   而你想问乙的时候，乙那两条挤不进来；
3. **别把自己挡在门外**（真踩过）：判断"谁能看全部"时，除了"本机"，**还要包含
   "在 IM 里以本人身份出现的你"**——否则你会在自己的聊天窗口里被当成"某个人"，
   只看得见关于自己的事实，然后以为她失忆了。

### 2.4 她自己的记忆 vs 从别人那儿听来的

**两条线，不许互相覆盖**：

- 她的自我认知（她怕什么、住哪）是**她自己的**；
- 从甲那儿听来的说法（"听说她住在山里"）是**甲的说法**，不是事实。

混在一起，她会拿别人的转述当自己的记忆，甚至拿它反驳你。

---

## 三、记忆怎么进来：不要直接写主库

从 IM 里提取的信息**不能直接进长期记忆库**。推荐**两段式**：

```
聊天内容 → 提取候选 → 待审核队列（人工过一遍）→ 才进主库
```

**为什么必须加这一道**：IM 里的话噪音极大——玩笑、转述、口误、别人的说法。
直接进库，你会得到一份"她以为某人是朋友、其实只是同事随口一提"的错误记忆。

审核界面最简形态就够（逐条显示、y 收 n 弃），但**这一步不能省**。

## 四、带话：让两个互不知情的人通过她传递信息

这是接 IM 之后**自然长出来的一个功能**，也是最有意思的一个。

### 4.1 机制

**甲在聊天里提到你** → 她用**自己的口吻**把这件事转达给你。

注意分寸：不是复述（"甲说他很累"），而是用自己的话把事带过来，
**同时保持"这是转达"的身份**——你该知道这是甲的事，不是她自己的事。

### 4.2 三条必须有的约束

| 约束 | 为什么 |
|---|---|
| **单向**：甲 → 你，不做双向 | 你回复什么**不会再转回给甲**。双向会变成"她替你们聊天"，且每次往返都是一次泄露风险 |
| **出口限流**：同一联系人在窗口期内**最多转达一条** | 否则甲说十句，你会被转达十次 |
| **可关闭**：每个联系人可以单独关掉转达 | 有人会不想被转达 |

⚠️ **还要防一件事**：转达内容**不能变成"她学到的事实"**。
"甲说他很累"是甲的状态，不是你的事实，也不该进她的自我认知。
**转达是消息，不是记忆。**

### 4.3 称呼要按人来

家人不会叫你网名。转达时用的称呼**每个联系人可以不一样**，
否则她转达时会喊你网名，在场的人一听就不对。

## 五、必须在代码里做、不能只靠提示词的事

| 事项 | 为什么不能只靠提示词 |
|---|---|
| **白名单校验** | 模型可能"觉得该回"就回了——必须在发出去之前用代码拦一道（尤其群聊：群名一个都不该放进来） |
| **发送去重 / 限流** | 连发、深夜刷屏是模型不守规矩时的常见表现 |
| **发送前清洗** | 内部标记（情绪标签、`[记住:]`）必须**在代码里**剥掉再发 |
| **消息顺序** | 攒批与逐条的时序要确定，否则会出现"回了一句已经过期的话" |
| **失败要响** | 发送失败必须报出来——静默失败会让你以为她在正常聊天 |

**判断标准一句话**：**凡是不允许出错的地方，都要写成代码分支，不能写在提示词里。**

---

## 六、如果只做一件事

**先做"只读"版本**：她能看到消息、能生成回复，但**回复只写进日志、不真发出去**。

跑一两周，把"你会怎么回"和"她会怎么回"对一遍——**看清她在什么时候说错话**，
再决定要不要让她的手指真的落到发送键上。这一步几乎零成本，能避免绝大部分事故。

---

## 附：这一层为什么没进仓库

不是技术原因，是**它天然携带真实社交关系**：联系人是谁、你们之间说过什么、
别人的隐私——全部无法脱敏，脱成示例就失去意义了。

所以这里只讲结构。真要动手，建议从"只读版"开始，跑在**你愿意承担后果的账号**上。
