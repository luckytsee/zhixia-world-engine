## 0. 一句话说清

**伴侣可以自己决定记住什么，而她说要记的就必须记得住。**
**她可以改主意，但不许假装自己没说过。**

这是与现有 `facts` 并列的一条**新链路**，不是它的扩展。理由见第 1 节。

### 0.1 ⚠️ "谁在决定"——必须说清，这里最容易拧

**决定权 100% 在她。** 她**主动写标记**，系统才记：

| ✅ 是 | ⛔ 不是 |
|---|---|
| 她在回复里写 `[记住:...]` ⇒ 记 | 系统从她的话里**提取**"她觉得重要的" |
| 这是**她的显式动作** | 系统对闲聊的**自动捕获** |
| 系统的责任：**别把她要记的东西弄丢** | 系统的责任：判断该不该记 |

⚠️ **`[记住:...]` 是唯一入口。** 她用自然语言说"这个我得记着""我记一下"**不算**——
否则又变成系统在猜她的意图了。（这条写在这里，防止将来为"她明明说了要记却没记"打补丁。）

⚠️ **一个诚实的前提**：这个动作**是要教的**——人格里得写一段"你可以决定记住一些事"。
**教她 = 在影响她做什么决定。** 影响多大要跑起来才知道（可能一句不记，可能每句都记）。

## 1. 为什么要新链路，而不是给 facts 加字段

现有 `facts` 表**结构上承载不了这个机制**，四个硬限制：

| # | 限制 | 后果 |
|---|---|---|
| 1 | `key TEXT PRIMARY KEY` | 同一个 key 物理上只能一行 ⇒ **只存当前快照，存不下时间线** |
| 2 | 只有 `first_learned` / `last_confirmed` | **分不清"她说的"和"系统提取的"**（只能靠 evidence 字符串硬凑） |
| 3 | 提取提示词写死"只记**关于作者的**稳定信息" | 她的自述被**契约主动排除** |
| 4 | `_visible_facts` 是按"人 × 人"的星形矩阵 | 世界事实没有"关于谁"这个维度，塞进去只会落进 `_UNKNOWN_SUBJECT` |

**结论：不在 facts 上打补丁，新建独立表。** `facts` 原样不动（它管"关于作者"，工作正常）。

## 2. 四层记忆的分工（2026-09-28 作者定稿）

> ⚠️ 本节替换了早前"三类写死的边界"——那版把几个概念混在一起了。
> **核心原则**：不要让每句话都变成设定，也不要因为它不是"核心设定"就把已经形成的自我认知丢掉。
> **经历先作为经历存在；只有真正有意义的经历，才逐渐沉淀成长期记忆。**

| 层 | 定义 | 例子 | 生命周期 |
|---|---|---|---|
| **`facts`** | **已确认的、关于对方的事实** | 对方的固定信息（住哪／在读什么／生日） | 长期 |
| **`world_notes`** | **伴侣自己形成、并决定长期保留的认知** | 我怕雾／我喜欢听风／我这儿没有中秋那套 | 长期 |
| **`episodes`** | **最近发生过的经历** | 今年中秋我坐在树根上看月亮 | **有生命周期，可升级** |
| **session state** | 今天／现在的临时状态 | 今天有点困／刚醒没多久 | **不持久化** |

### 2.1 三处最容易混的地方

**① `world_notes` ≠ "关于伴侣自己的设定"**（早前的错误理解）
它是"**伴侣自己形成并选择保留的认知**"，可以是：
- 关于自己的："我住在大树根底下""我怕雾"
- 关于她所处世界的："林子里还有其他精灵""我这儿没有中秋那套习俗"
- **关于作者的主观看法**："我以前以为你很早睡""我觉得你经常熬夜"

⚠️ 最后一种必须与 `facts` 区分：`facts` = 已确认的事实；`world_notes` = **她自己的认知/判断**。
两者冲突时**以作者当前明确说的为准**，但**不删她过去的判断**（她可以说"我以前以为……"）。

**② 稳定认知要记——早前"别滥用"的规则过宽了**
判据从"这件事以后我还希望自己记得吗"**明确成**：

> **"这是不是关于『我是什么样的人／我生活在什么样的世界里』的一项稳定认知？"**

| 记 ✅ | 不记 ❌ |
|---|---|
| 我怕雾／我喜欢晚上听风／我很少出门／我喜欢甜的／我住在大树根下面 | 今天有点困／刚才有点生气／刚醒没多久 |

**③ 经历 ≠ 长期认知（关键修正）**
"今年中秋我坐在树根上看月亮"是**真实经历**，但**不该一发生就永久进 `world_notes`**——
它先作为 `episode` 存在。

**记忆生命周期**：
```
刚发生 → 7天内高优先级、容易回忆
       → 7~30天仍可检索，逐渐降低优先级
       → 超约30天、没被再次提起 → 默认不再进入上下文
```
⚠️ 这里的"遗忘"指**不再主动检索/注入，不是物理删除**（现有 `archived` 机制就是这个语义）。

### 2.2 `episode → world_notes` 的升级通道

一件经历满足**任一**条件可升级为长期 `world_note`：
1. 被**反复提起**（说明对双方连续性有意义）
2. 伴侣**自己后来主动想起**它
3. 它与已有的重要认知**产生关联**
4. **伴侣自己判断**"这件事我以后还想记得"

例：中秋看月亮先是 episode；若反复提起、或她自己觉得值得留 → `[记住:今年中秋我坐在树根上看月亮]`
→ 进 `world_notes`。而"昨天踩到一块石头"这种，**自然淡出即可**。

⚠️ **`[记住:...]` 仍是主要机制；系统不要替她自动把普通聊天全部抽成 `world_notes`。**

### 2.3 变化不能覆盖历史

`world_notes` **不是"当前正确设定表"**：
```
过去：   我怕雾。
后来：   有人陪我走的时候，好像没那么怕了。
再后来： 现在我其实已经不太怕雾了。
```
**不要把第一条直接改成第三条，也不要删除过去**——保留认知变化的历史。
这样她才能说："我以前确实很怕雾，不过后来慢慢没那么怕了。"
**这才是"成长"，而不是数据库更新。**

✅ 现有实现天然满足：`WorldNotesStore.add()` **只 INSERT、没有 UPDATE**，三条会并存。

**框架本身不写死任何具体设定**：她不叫什么世界、她怕不怕打雷——全部是她自己记进笔记，或者你往 persona 里填。

## 3. 世界笔记机制 `[记住:...]`

### 3.1 她的动作

她回复里写标记：

```
[记住:我窗台上摆了三盆花]
```

- **这是她的决定**，系统不做判断、不筛选、不等第二次提到
- 系统**信任她**——记什么由她定，这跟"记什么是系统判断"是完全不同的机制
- ⚠️ **不是**对闲聊的挖掘：闲聊不记，只有她显式声明才记

### 3.2 处理全在电脑，手机不处理

```
手机（鸿蒙 App）                    电脑（伴侣本体）
─────────────────                  ─────────────────────────
显示时剥掉标记                      全部处理在这里：
上传时**保留原文**（含标记）  ──→     剥标记 → 落库 → 检索 → 注入
   ↑ 只改 cleanSpeech 一处          ↑ 单写点，手机从不写库
```

**"显示时剥、上传时留"——两个方向不能搞反。** 若手机剥完再上传，电脑就见不到标记了。

⚠️ **手机上她记的东西当场不生效**，要等你回电脑、`POST /sync/sessions` 推送后才进库。
这是"单写点在电脑"的必然代价，**架构上是对的**（手机只读 ⇒ 永远不会写脏数据 ⇒ 不需要冲突仲裁）。

### 3.3 表结构

**第一步只建这四列**（最小集）：

```sql
CREATE TABLE world_notes (
    id             TEXT PRIMARY KEY,   -- uuid4 hex
    ts             REAL NOT NULL,      -- 她什么时候记的
    text           TEXT NOT NULL,      -- 她记的原文
    origin         TEXT NOT NULL,      -- zia_said | owner_told（见 3.7）
    source_turn_id TEXT                -- ★ 这条笔记出自哪一轮对话（见 3.6）
);
CREATE INDEX idx_world_notes_ts ON world_notes(ts);
```

**数据库**：`data/zia_world.db`（**独立库**，与 `memory.db` 物理隔离）。
理由：世界链路坏掉时，桌面伴侣本体照常跑。

### 3.4 `source_turn_id`：日志追踪，不是世界建模

**目的不是检索，是回答"她为什么这么认为"。**

⚠️ **为什么必须写入时固化、不能事后反查**（作者 2026-09-28 指出）：
本项目的对话历史**本来就在被正常机制删掉**——桌面 `session_turns` 干净退出才写、
强杀就丢（P9）；工作记忆超 20 轮压成摘要；微信会话冷场 30 分钟就清空。
**"从日志里反查"这条路会随系统运转自己烂掉。** 所以写入时就得记下来。

**实现选型（倾向）**：不给 `session_turns` 的消息加 id（那会牵动压缩 / pop / 提取器多处），
而是存一个**自造的定位符**（如 `"<会话标识>-<第几轮>"`）。
**它不要求能反查原文，只要求能定位"是哪一轮"。**

⚠️ **已知局限（实现时如实对待）**：
- **手机端会退化**：手机是"攒着推回来"，拿到的原文隔了几小时，**轮次对不上**——
  很可能只能定位到"哪次上传批次"，做不到"哪一轮"
- **压缩会错位**：工作记忆压缩后轮次可能偏移

### 3.5 以下五个字段**预留、暂不建**

```sql
    -- 预留：等真实数据再加，现在建了大概率形状是错的
    key           TEXT,    -- 归一化键名（"窗台的花"）
    kind          TEXT,    -- entity | event | state | self
    valid_from    REAL,    -- 什么时候开始成立
    valid_to      REAL,    -- 什么时候不再成立（NULL = 仍成立）
    superseded_by TEXT     -- 被哪条取代（版本链）
```

**为什么不现在建**：它们解决的是"**同一件事随时间变化**"（窗台三盆花 → 搬走一盆）。
但**她会不会记这种会变的东西，现在完全不知道**。`facts` 表就是"存储设计早于真实需求"的产物，所以到处是补丁——**这个坑不踩第二次**。

⚠️ **和 `source_turn_id` 的区别**（作者 2026-09-28 指出的关键区分）：

| 类别 | 字段 | 解决什么 | 复杂度 | 现在做吗 |
|---|---|---|---|---|
| **日志追踪** | `source_turn_id`、`origin` | "她为什么这么认为" / "谁说的" | **低**（写入时记一个值） | ✅ **做**——不依赖对她行为的任何假设，**不做就永久丢失** |
| **世界建模** | `key`、`kind`、`valid_from`、`valid_to`、`superseded_by` | "同一件事随时间变化" | **高**（要理解语义、判冲突、建版本链） | ⏸ 等真实数据 |

**验收第一步之后，看她记什么，再回来定这些字段。**


### 3.6 检索与注入

- **检索**：子串 + 关键词命中（**不需要向量**——条数少时跟 `facts` 一个量级）
- **注入**：跟记忆块并列，加一句**约束**：
  > 这些是**你自己记得的事**，别反着说。
- **⚠️ 过滤（双保险）**：注入前挡掉"明显是外观/能力"的条目（含 `长发/绿发/精灵/衣服/立绘/长得` 等词）。
  理由：**LLM 不一定会听话，但过滤是确定性的。**

### 3.7 `origin`：解释"她为什么这么认为"的入口

⚠️ **这不是一个标记字段，是一条独立的设计线**（作者 2026-09-28 特别保留）。

**值域（契约的一部分，方便将来加值不用到处改判断）**：

| 值 | 含义 | 现在产生吗 |
|---|---|---|
| `zia_said` | **她自己说/决定的** | ✅ 是 |
| `owner_told` | **你告诉她的**（含纠正） | ✅ 是（走现有提取器进 `facts`） |
| `from_contact` | 联系人说的（微信虽灰度，童话说"他最近很忙"来源又不同） | ⏸ 暂不产生 |
| `world_made` | 她的世界动作（"我把花挪到窗台了"） | ⏸ 暂不产生 |

**为什么值域现在就要列出来**：将来加值的时候，若各处判断是散落的 if，会到处漏。

**它真正的用途——回答"她为什么搞错了"**：

```
world_notes:  我窗台上有三盆花        zia_said
              其中一盆已经送人了      zia_said
facts:        作者现在在外面          owner_told
```

**"她的记忆"和"你告诉她的事实"不是同一种来源** ⇒ 冲突时一眼看出一路是自己认定的、
一路是你说的，**而不是笼统地"覆盖掉"**。
这是将来做"**伴侣为什么这么认为**"的基础。


### 3.8 与现有系统的交汇：你说的 = 纠正

- 她的猜测进 `world_notes`（`zia_said`）
- **你的纠正走现有提取器进 `facts`**（`owner_told`）——**零新机制**，提取器本来就在记"关于作者的"
- ⚠️ **矛盾处理**（本设计唯一的冲突规则，先这样）：两边都可能被注入 ⇒
  提示词里明确"**以作者说的为准**"

⚠️ **已知局限**：删了笔记 ≠ 她忘了（见 5.4）。


她现在的自我信息源只有 persona 里那几句话，所以**很容易把 persona 抄回去**，记出
`[记住:我有浅绿色长发]` 这种东西。这不是她错，是**信息源太单一**。

所以在教她这个动作的说明里**必须同时写清"什么不要记"**：

```
你可以决定记住一些事。但有几类**不要记**：
- 你的长相、衣着——那些你本来就知道，不用记
- "我能认出他"这类能力——那是你天生会的，不是要记的事
- 你住哪儿、世界叫什么——这些以后会单独告诉你
```

### 3.9 ⚠️ "不能反悔"的准确含义（防穿帮，不是不许变）

**两个目的会导出完全不同的规则**（作者 2026-09-28 拍板：**选第一种**）：

| | 规则 | 结论 |
|---|---|---|
| **第一种：防自相矛盾** | 不许**假装自己没变过**；**允许改主意** | ✅ **采纳** |
| 第二种：哲学意义的承诺不可撤销 | 连改主意都不行 | ⛔ 否掉——**人是会变的，会改主意正是"是个人"的标志之一** |

**规则**：

```
✅ 允许："我上次说怕打雷，现在好像不太怕了"
⛔ 禁止："我从没说过怕打雷"          ← 穿帮

判据：改了要**留下痕迹**，而不是**抹掉痕迹**
```

**⭐ 这条直接决定了数据模型的形状**：
`valid_from` / `valid_to` / `superseded_by` 三个预留字段，**存在的理由就是"允许改主意但保留历史"**。
若规则是"连改主意都不行"，那只需两列（当前值 + 历史），**不需要"版本链"这个概念**。

⚠️ **与本项目已有事实的对应**：K1 现象（[7.5 节](07_项目选型与评估.md)）——
"发送行为不记账"导致她**否认自己发过的图/语音**（"我还没出声呢"）。**这与"我从没说过怕打雷"是同一个病。**

**注入时的措辞**（不能只写"别反着说"，太粗）：

> 这些是**你自己记得的事**。你可以改主意——但**不能说自己没说过**。

## 4. 通道语义：窗口意味着什么

**她不是通过"看"知道你在哪，而是通过"你从哪个窗口来"。**

| 窗口 | 你在哪 | 她该怎样 | 状态 |
|---|---|---|---|
| **桌面** | 住处（电脑前） | 在场陪着你 | ✅ 在用 |
| **手机** | 外面 **或** 在床上 | 陪着你，但隔了一层 | ⚠️ 见下 |
| 微信 | — | — | 已灰度（`[wechat] enabled=false`） |

**这个设计的好处**：不需要任何感知能力（`[perception]` 是关的、截图要手动触发），
而且 **100% 可靠**——你从桌面找她 = 你在电脑前，这是**定义**不是推断。
对比：现在她想说"你在哪"只能靠猜，而**猜就会错**（"下午两点被写成凌晨两点"那次事故）。

### 4.1 "在外面"还是"在床上"——她随便说，你纠正

**第一版不做传感器、不做时间推断。** 原则（作者 2026-09-28 定）：

> **她随便说呗，我再纠正她，认可了继续。**

- 她可以说"你在床上吧" → 这**本身就是一条世界笔记**（`origin=zia_said`，她猜的）
- 你答"嗯，躺下了" / "不对，我在外面" → 走**现有提取器**进 `facts`（`origin` 概念上 = `owner_told`）

**于是"通道语义"不需要写死成一张表**——它并进了机制本身，**跟世界笔记是同一条路**。

⚠️ **矛盾怎么处理**：你的纠正进了 `facts`，她的猜测留在 `world_notes`，两边都可能被注入。
**注入时以你说的为准**（提示词里明确写这一条）。这是本设计里**唯一的冲突处理规则**，先这样，不够用再说。

⚠️ **想让她主动知道**（不靠你告诉）需要读手机传感器（充电中/静止/连常用 WiFi）——
那是**手机端新功能、要重新打包**，放进第 7 节"预留"。

## 5. ★事后修正通道（作者 2026-09-28 定）

### 5.1 定位：不是审核，是**可观测性**

作者的真实诉求（原话）：

> **"不让我怕她胡言乱语了我都不知道为什么。"**

| | 审核 | 本工具 |
|---|---|---|
| 目的 | 防止坏数据进库 | **出事时能查到原因** |
| 时机 | 记之前 | **记之后、出问题时** |
| 关键 | 拦住 | **看得见** |

**所以它的核心功能不是"能删"，是"能查"。**

### 5.2 形态：与 `改记忆.bat` 同套路

```
伴侣世界笔记.bat  →  tools/edit_world_notes.py
```

沿用现有 bat 的纪律（`改记忆.bat` 已经验证过的写法）：

- **bat 纯 ASCII**（cmd.exe 按 ANSI 读文件，中文会被误解析）→ **中文 UI 全由 Python 打印**
- 用 `.venv\Scripts\python.exe`（**不是 pythonw**，要有控制台输出）
- 跑完 `pause` 停住好看结果
- 在系统启动项里加一个入口即可

### 5.3 界面要能回答"为什么"

```
  伴侣世界笔记（新→旧）

  [12] 09-28 14:23  我窗台上摆了三盆花            zia_said
       触发上下文（第 3 轮）：
         作者：你窗台上放东西了吗？
         伴侣：我窗台上摆了三盆花。
  [11] 09-28 11:05  我不喜欢被叫小朋友            zia_said
       触发上下文（第 7 轮）：
         作者：叫你小朋友行不行
         伴侣：……行吧，但我不喜欢。

  [数字] 看详情 / [d 数字] 删除 / [q] 退出
```

**带上下文是核心**——没有它，"她为什么记这个"就查不出来。
上下文由 `source_turn_id`（3.4）定位，**不是事后从日志反查**。

⚠️ **显示口径要说清**：取的是 `source_turn_id` 指向的**那一轮**，
**不是"因果关系"**——她可能在隔几句之后才写标记，那一轮可能只有她的话、没有你的问句。
工具里显示"**那一轮**"，别让人误以为它在解释因果。

⚠️ **取不到时如实显示**"（上下文已不可用）"，**不要编**。

### 5.4 ⚠️ 已知局限：删了笔记 ≠ 她忘了

**删掉一条笔记，她下次可能又记一遍**——因为她的对话历史里还留着她自己说过的话。

**这不是 bug，是设计的事实**，必须写在工具里（或 README 里）让人知道，
否则作者会以为"删了就干净了"，然后困惑"为什么她又说了"。

**真正的"让她忘掉"**需要清对话历史 / 压缩摘要，那是另一件事，不在本规格。

### 5.5 显示策略

- **聊天里：剥掉不显示**（跟 `[happy]` / `[图:标签]` 一样）⇒ 她说话自然，不出戏
- **日志里：留痕** ⇒ 你能查证
- **bat 里：全部可见可删** ⇒ 出问题时能查原因

### 6.1 验收（当天可验，不用等几天）

| # | 验什么 | 怎么测 |
|---|---|---|
| 1 | 她会不会记 | 说一句"你桌上放个杯子吧" → 查库/bat 里有没有 |
